# QyranEye — детекция падений людей на видео с дрона

Система смотрит записанное видео с дрона (FIMI X8 SE, 4K, высота 5–20 м, камера под углом
или строго вниз), находит людей, следит за каждым и поднимает тревогу **FALL**, если человек
быстро перешёл из положения «стоит» в «лежит» и лежит дольше 4 секунд. Результат — видео
с рамками и CSV со временем тревог. Всё работает локально на MacBook (Apple Silicon), без интернета.

## Как это работает

```
видео ──► уменьшение до 1080p ──► YOLO26s (люди) ──► BoT-SORT (номер каждого человека,
          с поправкой на движение дрона) ──► ракурс (под углом / сверху) ──► поза в кадре
          (стоит / переход / лежит; под углом у крупных людей — по точкам тела) ──► сглаживание 0.5 с ──► логика падения ──► видео + CSV
```

Логика падения (`fall_logic.py`) для каждого человека:

| Состояние | Когда | Рамка |
|---|---|---|
| UP | стоит или идёт | зелёная |
| FALL? | быстро оказался на земле (есть точки тела — плечи сдвинулись относительно ног ≥ 1.2 роста/с; нет — переход за ≈ 1–2 с) | жёлтая |
| **FALL** | после FALL? лежит 4 с, лежит сейчас и не перемещается | **красная, событие в `<имя>_events.csv`** |
| LYING | лежит, но падения не было (лёг медленно или уже лежал) | синяя |
| LYING + **CHECK** | лежит и не двигается 10 с, а тревоги нет (мог упасть медленно или потерять сознание) | синяя, надпись CHECK, строка в `<имя>_checks.csv` |

Перед тревогой система проверяет, что человек правда лежал и не двигался (иначе это человек, который
встал и пошёл, или сумка, которую несут) — тогда FALL? отменяется. И что его **правда видели**: лежащим
не меньше 70 % всех кадров этих 4 секунд (кадры, где его не было видно, не считаются), а с нынешним номером —
хотя бы 2 с. CHECK — не тревога о падении, а просьба к оператору посмотреть: решает человек.

Поза определяется одним из способов (`pose_mode` в `config.yaml`):

* **geometry** (по умолчанию) — правила по форме рамки. Под углом: стоящий — узкая высокая рамка,
  лежащий — широкая (рамка, у которой ширина/высота ≤ 0.8, «лежит» не считается). Сверху: стоящий — компактное «пятно», лежащий — вытянутая полоса.
  Каждый человек сравнивается с ним же самим, пока он стоял.
  **Под углом у людей от 80 пикселей** вместо рамки работают точки тела (`crop_keypoints`): человека вырезаем, увеличиваем
  до 384 px и ищем плечи, бёдра, щиколотки (YOLO26n-pose). Так «присел» и «лежит» различаются. Сверху и для мелких людей
  точки не помогают, там остаётся рамка.
* **classifier** — нейросеть позы (`pose_cls.pt`) смотрит на картинку человека.
* **hybrid** — правила + нейросеть: сеть отменяет ложное «лежит» и отсекает «не людей», но падение
  засчитывается только по быстрой смене формы рамки.

## Установка

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

Модели: `yolo26s.pt` (детектор) Ultralytics скачает сам при первом запуске; `pose_cls.pt`
(нейросеть позы) лежит в проекте.

> Если `source .venv/bin/activate` не работает (окружение переносили из другой папки) —
> запускайте напрямую `.venv/bin/python ...` или пересоздайте окружение командами выше.

## Запуск

```bash
.venv/bin/python main.py видео.mp4 --view oblique   # камера под углом (45–60°)
.venv/bin/python main.py папка/ --view nadir        # камера строго вниз; все видео в папке по очереди
.venv/bin/python main.py видео.mp4 --view auto      # угадать ракурс (ненадёжно, если людей 1–2)
.venv/bin/python main.py видео.mp4 --view oblique --config другой.yaml
```

Результат в `results/`: `<имя>_fall.mp4` (рамки, состояния, ракурс) и `<имя>_events.csv`
(время начала падения, время тревоги, кадр, координаты рамки, скорость, доля «лежит»).

Скорость на MacBook Air: ~11–20 кадров/с для видео 1080p (минута видео ≈ 1.5–3 минуты обработки).
Длинные обработки запускайте с подключённой зарядкой и открытой крышкой
(`caffeinate -i .venv/bin/python main.py ...` не даёт Mac уснуть от бездействия).

## Настройки (`config.yaml`)

Все пороги — в `config.yaml`, у каждого комментарий «что это и почему такое значение».
Главные переключатели:

| Параметр | Значение | Что делает |
|---|---|---|
| `model` | `yolo26s.pt` | детектор людей |
| `tracker` | `botsort` | трекер с поправкой на движение дрона (`bytetrack` — без неё) |
| `camera_view` | `auto` | ракурс по форме людей в начале видео; меньше 3 человек — `oblique` и предупреждение. Надёжнее задать `--view` |
| `pose_mode` | `geometry` | способ определения позы (`classifier`, `hybrid`) |
| `crop_keypoints` | `true` | точки тела у крупных людей под углом (`false` — только рамка) |
| `fall_speed_min` | `1.2` | с какой скорости (ростов в секунду) это падение, а не «лёг сам» |
| `lying_alarm_s` | `4.0` | сколько секунд лежать после падения до тревоги |
| `fall_transition_s` | `0.75` | насколько быстрым должен быть переход, чтобы считаться падением |

## Проверка

### 0. Все главные числа одной командой (10–40 секунд)

```bash
.venv/bin/python eval/report.py --md docs/report.md
```

Прогоняет текущие `fall_logic.py` и `config.yaml` по записанным входам всех роликов (Okutama, NOMAD, снег, MOD20)
и печатает таблицы ниже, а в конце — «Все проверки пройдены» или что именно не так (в том числе если каких-то
записей нет). Режимы с нейросетью: `--set pose_mode=hybrid --net extra`, `--set pose_mode=classifier --set pose_upright_max=0.3`. **Числа в этом README берутся
только отсюда** (последний отчёт: [docs/report.md](docs/report.md)). Нужны записанные входы и точки тела
в `eval_results/` (их делает `eval/record_inputs.py`; в git не хранятся).

### 1. Синтетические тесты логики (секунды)

```bash
.venv/bin/python tests/test_fall_logic.py
```

61 придуманный сценарий (падение, медленно лёг, упал и встал, смена номера человека,
сумка рядом, дрон плывёт, рамка у края кадра, нейросеть и т.д.). Печатает OK / FAIL и ИТОГ.
Известное ограничение — тест **N4**: при съёмке сверху очень широкий шаг на месте
похож на «лежит» по форме рамки.

### 2. Проверка на видео с разметкой Okutama-Action (минуты)

```bash
.venv/bin/python eval/evaluate.py okutama_lying     # 4 ролика с лежащими людьми, ~10 мин
.venv/bin/python eval/evaluate.py heldout           # 3 ролика, ~8 мин
.venv/bin/python eval/evaluate.py untouched         # 4 ролика, ~17 мин
.venv/bin/python eval/evaluate.py val               # 7 проверочных видео обучающей части, ~25 мин
.venv/bin/python eval/evaluate.py okutama_lying --config другой.yaml   # сравнить настройки
```

Печатает: сколько размеченных людей система нашла, у скольких правильный статус,
сколько ложных «лежит» и ложных тревог. Наборы описаны в `eval/sets/*.csv`; для них нужны
папки `drone videos/`, `okutama_lying/` и `okutama_train/` (см. «Данные» ниже).

Для подбора порогов без повторного запуска нейросетей: `eval/record_inputs.py` записывает,
что получает логика (вместе с точками тела), а `eval/replay.py` прогоняет только логику с любыми настройками
(инструкции — в начале файлов). На этой записи работают ещё два скрипта:

```bash
.venv/bin/python eval/select_mode.py eval_results/inputs/val            # выбор режима и порогов на проверочных видео
.venv/bin/python eval/compare_modes.py eval_results/inputs/okutama_lying okutama_lying   # сравнение режимов
```

## Результаты на Okutama

**Было → стало на одних и тех же 4 роликах** (`okutama_lying`; начальная версия измерялась только на них):

| | Начало проекта (yolo26n-pose) | Сейчас (настройки по умолчанию) |
|---|---|---|
| Людей найдено | 12 % | **87 %** |
| Правильный статус у найденных | 56 % | **87 %** |
| Правильный статус у всех размеченных | 7 % | **76 %** |
| Ложные тревоги FALL | 0 (почти никого не находила) | **0** |

**Сейчас на всех 11 роликах:** найдено 86 %, правильный статус у найденных 86.8 %,
у всех размеченных 74.4 %, ложных тревог FALL 0; на 7 проверочных видео ложных тревог тоже 0.
Ракурс каждого ролика — тот, что выбрал при записи авто-ракурс; для ясных роликов он совпадает с видимым глазами
(числа из `eval/report.py`).

**Сравнение режимов позы** (11 роликов, `eval/compare_modes.py`):

| Режим | Правильный статус у найденных | Лежащие с LYING* | Ложные «лежит»** | Ложные тревоги |
|---|---|---|---|---|
| **geometry** (по умолчанию, с точками тела) | 86.8 % | **64.8 %** | 7.8 % | **0** |
| classifier (сеть v1, порог 0.3) | 89.4 % | 58.8 % | 8.3 % | 3 |
| hybrid (правила + сеть v2) | **90.4 %** | 25.5 % | **0.8 %** | **0** |

\* от всех размеченных лежащих, включая ненайденных; FALL? и FALL тоже засчитаны.
\*\* LYING, FALL? и FALL у не лежащих людей.

**Как выбран режим по умолчанию (честно).** Заранее записанное правило (`eval/select_mode.py`,
7 проверочных видео) выбрало `classifier` с сетью v1. Мы его не взяли: на тестовых роликах он дал
2 ложные тревоги (сейчас, при ожидании 4 с, — 4). `geometry` оставлен **с учётом результатов на тестовых роликах**, поэтому это
не независимый выбор. Пороги `hybrid` (0.1 и 0.7) взяты вручную из таблицы проверочных видео среди
почти равных вариантов. На тех же проверочных видео выбиралась лучшая эпоха обучения сетей,
поэтому сети там выглядят лучше, чем есть.

**Правило «рамка должна быть и сама по себе широкой»** (порог 0.8, тот же `aspect_abs_upright_max`).
На ролике NOMAD (Actor035, 10 м) очень узкий стоя человек присел, рамка выросла в 1.8 раза, и была ложная
тревога. Теперь «лежит» — это выросла в 1.8 раза **и** ширина/высота больше 0.8. Было → стало:

| | Было | Стало |
|---|---|---|
| NOMAD Actor035 (присел, потом лёг; падения нет) | ложная тревога | тревоги нет, LYING |
| Снег (Mixkit): споткнулся, 5 с на четвереньках, встал сам | тревога на 6.1 с | тревога на 6.2 с |
| Ложные «лежит», 11 тестовых роликов | 12.7 % | 10.0 % |
| Правильный статус у найденных, 11 тестовых роликов | 81.9 % | 84.4 % |
| Лежащие с LYING, 11 тестовых роликов | 67.2 % | 67.2 % |
| Лежащие с LYING, 7 проверочных видео | 19.2 % | 18.7 % |
| Ложные тревоги на Okutama | 0 | 0 |

Порог выбран на этих же роликах (пробовали 0.7–1.1; от 0.9 терялась тревога в снегу на 6 с; позже выяснилось, что это не потеря сознания, а человек споткнулся и встал), поэтому это
«цифры разработки». Режимы classifier и hybrid от правила не изменились.

**Правило «лежащий, который идёт, не лежит»** (для geometry и hybrid, новых порогов нет). LYING снимался, только если
человек «стоит» 2 с подряд. При ходьбе рамка то шире, то уже, и LYING мог держаться долго (NOMAD Actor099 — 14 с).
А пока LYING не снят, новое падение система не видит. Теперь LYING снимается и тогда, когда 2 с подряд поза
переходная **и** скорость больше 0.5 длины тела в секунду. Тревогу FALL это правило не снимает. Было → стало (geometry):

**Тревога только про того, кого видели, и сигнал CHECK (26.11.2026).** После исправлений `395edaf` на проверочном
видео 2.2.9 появилась ложная тревога: двое несли стол, дрон быстро летел, человек (57 px, без точек тела) трижды
сменил номер, и тревога пришла в первом же кадре четвёртого номера. За 4 с ожидания его видели лежащим 24 кадра
из ~60 — правило считало долю только среди увиденных кадров (24 из 24). Теперь нужно и то и другое:
видели лежащим ≥ 70 % **всех** кадров последних 4 с, и нынешний номер виден ≥ 2 с (`recover_s`, новых чисел нет;
через 8 с после падения возраст номера не важен, чтобы частая смена номера не теряла тревогу).
Каждое из двух условий по отдельности снимает эту тревогу. Было → стало:

| | Было (`395edaf`) | Стало |
|---|---|---|
| Ложные тревоги, 7 проверочных видео | 1 (2.2.9) | **0** |
| Настоящее падение в снегу | тревога на 21.04 с | тревога на 21.04 с (видели 51 кадр из нужных 35) |

| MOD20 (55 роликов), NOMAD | 0 тревог | 0 тревог |

Сначала «видели лежащим» копилось с начала падения без ограничения по времени: того, кого видно урывками, тревога
не снималась, а только откладывалась (тест W5: виден 40 % кадров, номер меняется каждую секунду — тревога на 11.7 с
про номер, которому 0.34 с). Теперь окно скользящее, последние 4 с; в W5 тревоги нет. Правило стало только строже,
поэтому ложных тревог прибавиться не может. Падение в снегу: за 4 с до тревоги его видели во всех кадрах, тревога
та же; на видео после этой правки ещё не перепроверено (`eval/report.py`).

Новый сигнал **CHECK** («лежит без движения 10 с», не тревога): на Okutama 4 сигнала, **все 4 на размеченных лежащих**,
на NOMAD, MOD20 и снеге — 0. При 5 с были бы ещё сигналы на сидящих и идущих, при 20 с — только 2 из 4. 10 с выбраны
по этим же данным, поэтому это тоже «цифры разработки».

**NOMAD, два новых ролика целиком, до точек тела** (Actor042 и Actor099, 10 м, 2 минуты; пороги на них не подбирались, кроме правила про ходьбу):

| Режим | Тревог, когда человек лёг (из 2) | Ложных тревог |
|---|---|---|
| **geometry** | **2** | 0 |
| hybrid (сеть v2) | 0 | 0 |
| classifier (сеть v1, порог 0.3) | 0 | 0 |

Люди там **легли сами** (быстро), а не упали: для системы это выглядит так же, как падение. Сети обучены на Okutama и на этой
съёмке лежащих почти не узнают. Правило с порогом 0.8 здесь ничего не изменило.

**Авто-ракурс «мало людей — под углом».** Из 11 роликов Okutama ракурс сменился у одного (1.1.8, там один человек, снято сверху):
85.5 → 85.1 % верных у найденных, ложные «лежит» 9.0 → 9.3 %, лежащие 67.1 % без изменений. С `--view nadir` для него — прежние числа.

**Ограничения (важно для защиты):**

* В Okutama **нет падений** — проверены только ложные тревоги и распознавание «лежит».
  Сколько настоящих падений ловит система, покажут только свои съёмки с постановочными падениями.
* Падение с потерей движения с верной тревогой у нас **одно** (снег, Mixkit), и по нему же выбрано ожидание 4 с.
* Если человек упал и его почти не видно (ушёл за край кадра, закрыт), тревога ждёт, пока его увидят лежащим
  ~3 с (70 % от 4 с), — приходит позже, но не теряется (тест W2). Если его так и не увидят — тревоги не будет.
  Если трекер часто меняет лежащему номер, тревога приходит не позже 8 с после падения (тест W4).
* Пока такая тревога ждёт, её всё ещё может отменить проверка «лежал и не двигался» (например, рядом прошёл
  помощник и рамки слились); тогда остаётся LYING и через 10 с — сигнал CHECK.
* CHECK проверен только на 4 лежащих людях Okutama; медленных падений с потерей сознания в данных нет.
* У мелких людей (меньше 80 px) и сверху точек тела нет: там рамка по-прежнему путает «присел» и «лежит».
* Точки тела считаются у всех крупных людей в каждом анализируемом кадре: около 20–80 мс на человека в экономном режиме.
* **Ракурс по форме рамок надёжно не определить** (лежащий под углом похож на стоящего, снятого сверху). На 22 роликах, начатых с
  разных секунд: если людей меньше 3, раньше ошибка под углом была в 22 случаях из 132, сейчас в 2; зато сверху 29 из 88 вместо 23
  (отрезки одного ролика похожи, это не независимые случаи). Ошибка «под углом принято за сверху» опаснее: 8 ложных тревог и пропуск
  падения; обратная ошибка тревог не добавляет, но лежащих находит 18 % вместо 71 %. **Поэтому при съёмке всегда задавайте `--view`.**
* Очень быстро лёг сам — для системы то же, что упал.
* Ползущий человек может получить UP вместо LYING (видно на искусственном примере); тревогу FALL это не снимает.
* За травой и кустами люди почти не видны (NOMAD, видно хотя бы половину человека): найдено 4 из 20 спрятавшихся лёжа
  и 19 из 65 спрятавшихся иначе.
* Присевший или наклонившийся человек может на несколько секунд получить LYING или FALL? (Actor035, Actor099).
* **Лежащий человек строго сверху, которого не видели стоящим** — слабое место: на 4 роликах с дрона
  (Pexels) он в двух всё время UP, в третьем 68 % UP и 32 % LYING, в четвёртом почти всё время «?».
  Нейросети позы на них тоже отвечают «стоит».
* Все 11 тестовых роликов Okutama уже использовались при разработке — цифры выше
  «цифры разработки», а не независимая проверка.
* Плохо: съёмка сверху людей, которые всё время что-то несут/толкают (ложные «лежит» до ~20 %),
  ролики с тенями и трибунами (детектор находит ~половину людей), падение строго вдоль линии
  взгляда камеры.

## Детектор и высота съёмки

`eval/detect_by_size.py` — только детектор, без трекера и логики: каждый 45-й кадр 11 роликов Okutama (436 кадров,
1980 размеченных людей), доля найденных (IoU ≥ 0.2, уверенность 0.25) по размеру человека в кадре 1080p и ракурсу.
Ракурс ролика — по форме размеченных рамок (сверху человек почти квадратный). 26.11.2026:

| | людей | как сейчас (1080p) | куски 2×2 на 1080p | imgsz 2560 | 4K, куски 2×2 | 4K, куски 3×3 |
|---|---|---|---|---|---|---|
| < 45 px | 362 | 62 % | 62 % | 58 % | 63 % | 63 % |
| 45–60 px | 654 | 76 % | 77 % | 76 % | 78 % | 77 % |
| ≥ 60 px | 964 | 89 % | 87 % | 89 % | 87 % | 87 % |
| **под углом** | 1276 | **89 %** | 89 % | 91 % | 90 % | 89 % |
| **сверху** | 704 | **62 %** | 61 % | 58 % | 60 % | 60 % |
| сверху, < 45 px | 175 | 49 % | 46 % | 35 % | 44 % | 47 % |
| лежащие, < 60 px | 32 | 53 % | 69 % | 62 % | 75 % | 69 % |
| лишние рамки на кадр | | 0.64 | 0.43 | 0.58 | 0.39 | 0.42 |
| секунд на кадр | | 0.08 | 0.17 | 0.15 | 0.35 | 0.34 |

Вывод: **с высоты теряем людей из-за ракурса «сверху», а не из-за разрешения.** Под углом детектор находит 89 %,
сверху — 62 %, и ни куски, ни 4K это не меняют: YOLO обучен на людях, снятых сбоку, человек сверху для него —
незнакомая форма (на 1.1.9 он не видит человека 25 px, зато принимает за человека тень прожектора). Куски
немного помогают с мелкими лежащими (53 → 69–75 %, но это 32 рамки из нескольких роликов) и вдвое уменьшают
лишние рамки, ценой в 2–4 раза более медленного детектора. Чтобы поднять «сверху», детектор нужно дообучить на
съёмке с дрона сверху. Разметка Okutama свободная (рамка больше человека), поэтому для мелких людей числа занижены
одинаково для всех вариантов.

## Нейросеть позы

```bash
.venv/bin/python tools/make_pose_crops.py okutama_train okutama_train/pose_crops        # v1: рамки разметки
.venv/bin/python tools/make_pose_crops_det.py okutama_train okutama_train/pose_crops_v2 # v2: рамки детектора
.venv/bin/python tools/add_lying_v1.py okutama_train/pose_crops okutama_train/pose_crops_v2
.venv/bin/python tools/train_pose.py okutama_train/pose_crops_v2 --name pose_v2 --epochs 15 --patience 4 --dropout 0.3
.venv/bin/python tools/eval_pose.py runs/classify/okutama_train/pose_runs/pose_v2/weights/best.pt okutama_train/pose_crops_v2/val
```

Две версии в проекте: `pose_cls.pt` (v1, рамки разметки) и `pose_cls_v2.pt` (v2, рамки детектора,
класс «не человек», искажения «как в видео», dropout). На проверочных картинках v2 реже ошибочно
говорит «лежит» (1.3 % против 1.9 %), отсеивает 56 % ложных срабатываний детектора, но узнаёт
меньше лежащих (54 % против 59 %). Детектор на обучающих кадрах 720p почти не находит лежащих,
поэтому «лежит» для v2 добавлено из v1 (`tools/add_lying_v1.py`).

Деление на обучение и проверку — по видео (7 видео только для проверки); видео 1.1.1 исключено,
потому что оно есть среди тестовых роликов.

## Данные и лицензия

* **Okutama-Action** — http://okutama-action.org/ (обучающая часть: кадры 1280×720, 5.3 ГБ;
  тестовая: видео 4K). Лицензия **CC BY-NC-SA 3.0**: только некоммерческое использование,
  с указанием авторов. Нейросеть `pose_cls.pt` обучена на этих данных — для коммерческого
  использования нужно согласие авторов или переобучение на своих данных.
  Статья: M. Barekatain et al., *Okutama-Action: An Aerial View Video Dataset for Concurrent
  Human Action Detection*, CVPR Workshops 2017.

  Response Scenarios*, WACV 2024; 100 человек, 10–90 м) — лицензия CC BY 4.0. Использованы ролики
  Actor042, Actor099 и кусок Actor035 (31 с); в git не хранятся.
* Модели YOLO — Ultralytics (AGPL-3.0).
* Большие данные и результаты (`drone videos/`, `okutama_*`, `results*/`, `runs/`) в git не хранятся.

## Как работаем вдвоём

1. Перед работой: `git pull`. Новая работа — в своей ветке (`git switch -c имя`), в `main` — через pull request.
2. Перед отправкой: `tests/test_fall_logic.py` и `eval/report.py --md docs/report.md` — оба без ошибок,
   новый отчёт — в том же коммите, что и изменение.
3. Числа в README и в сообщении коммита — только из `eval/report.py`, с номером версии.
4. Изменения `fall_logic.py` и `config.yaml` — только после согласия второго участника.

## Структура

```
main.py              запуск: файл или папка с видео
video_pipeline.py    детектор, трекер, нарезка людей для нейросети, видео и CSV

config.yaml          все пороги и переключатели
config_tiles.yaml    отличия от config.yaml: нарезка кадра на куски (для очень мелких людей)
pose_cls.pt          нейросеть позы v1
pose_cls_v2.pt       нейросеть позы v2 (для режима hybrid)
tests/               синтетические тесты логики
eval/                проверка на видео с разметкой, запись/повтор, report.py (все числа), fall_recall.py (съёмка FIMI)
docs/                план съёмки, деление данных (data_split.md), последний отчёт (report.md)
tools/               чтение разметки Okutama, нарезка картинок, обучение нейросети
```
